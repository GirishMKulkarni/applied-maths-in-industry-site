S13B · SQL — Ask Questions of the Tables Where Industry Keeps Its Data

The problem

For twelve sessions you have loaded data from CSV files into pandas and got to work. Here is the thing nobody told you: in a real company, nobody emails you a CSV. When Flipkart records your order, when PhonePe moves ₹50, when an insurer pulls up your policy, that record goes into a database, on a server, being written and read by hundreds of other people and programs at the same moment. Your future analyst job starts with asking that database questions, in a language called SQL.

Today is a short, one-hour session between the machine learning block and the finance block. No installs, no setup: we will work entirely in the browser on SQL Practice Online, on a small HR database (employees, departments, jobs) that looks exactly like the tables you would meet in a company.

The one idea

A database is a disciplined set of tables, and SQL is a language where you describe the answer you want, not the steps to get it.

In pandas you write code that says how to walk through rows. In SQL you write one sentence: "from employees, show first_name and salary where salary is above 80000." The database's job is to figure out how. That one switch, from how to what, is why SQL has survived fifty years of new technology, and why it is on almost every data-job interview sheet in India.

Picture a company's data as a big, tidy library of ledgers. Every ledger is one table about one kind of thing: employees, departments, jobs. SQL is how everyone, from a Python program to a Power BI dashboard, asks those ledgers questions without ever touching the shelves themselves.

How the hour runs

This is a 60-minute session, half conversation and half live demo. You follow along on your own laptop; the only thing you need is the browser link above.

  1. (5 min) Where industry keeps its data. Why CSVs die at company scale: thousands of users writing at once, crores of rows, rules like "salary cannot be negative" that must never break. A database server owns the data; analysts query it over the network. UPI, IRCTC booking windows, telecom billing all run this way.
  2. (10 min) What SQL is and why it is required. Tables, rows, columns; the core verbs SELECT ... FROM ... WHERE. Declarative vs step-by-step, shown by comparing a pandas snippet with the same request as one SQL sentence. Then the industry reasons: it is the shared language across tools (Python, Excel, Tableau, any web app), it guards the data while many people use it at once, and it scales from 10 rows to 10 billion.
  3. (10 min) How data is stored in industry. Primary keys (the unique ID of a row), foreign keys (an ID in one table pointing at a row in another). We open the site's ER diagram and read its three tables: employees points at departments and jobs. Also the honest map of where data really lives: the operational database that runs the business, the warehouse that stores its history for analysis, and plain files for everything else.
  4. (12 min) Normalization, and why we normalize. We take one wide messy sheet (employee name typed next to department name and location repeated on every row) and try to update a department's location. It is wrong on some rows now. That is an update anomaly, and it is why we split data so each fact lives in exactly one place. Normal forms are just the rulebook for the split; we also see when companies deliberately bend it back for speed (dashboards).
  5. (8 min) Flavours of SQL. SQLite, PostgreSQL, MySQL, SQL Server, Oracle: same standard sentence, slightly different accents. Who uses what (banks and government on Oracle/SQL Server, startups on PostgreSQL/MySQL, every phone app on SQLite). We switch engines in the site's dropdown and watch what changes and what does not.
  6. (12 min) Hands-on lab. On the Select Statements topic (12 guided exercises) we solve together: pull all columns, pick columns, DISTINCT, computed columns like salary * 0.10, aliases, then the capstone projection. The same database ships with this session as data/hr_database.sql (download below), so at home you can load it into sqlite3 and keep practising on your own machine. You keep going after class; finishing all twelve is the homework.
  7. (3 min) Wrap-up. Where SQL meets what you already know (pandas can talk to databases too, via read_sql), and how the finance block starting next week begins with pulling market data the same way.

Stretch moments (optional)

Two corners of today's database reward a second look.

The manager is also an employee. Look at manager_id in employees: it holds another employee's employee_id. One table pointing at itself, which is how reporting hierarchies are stored everywhere. Ask the ER diagram, then try to imagine drawing the org chart from it.

One query, five homes. In the editor, run SELECT 1 + 1 AS result with no table at all. SQLite accepts it happily. Oracle insists you add FROM dual, a one-row dummy table, which is why the site runs Oracle as a guided comparison instead of live execution. Small accent, big clue: dialects differ at the edges, and knowing the edges is what interviews test.

For the mathematically curious (optional)

Everything above is enough for the hour. This box adds the formal spine, and none of it is needed to finish.

A relation is a set of tuples: a table is a set of rows, so order carries no meaning and duplicates are excluded by design (which is why DISTINCT feels natural). A key is a set of columns whose values identify a tuple uniquely; the primary key is the chosen identifier, and a foreign key asserts that values in one table must exist as keys in another, which is a constraint enforced at write time. Normalization is the theory of decomposition driven by functional dependencies: if column B is determined by column A (a department_id always yields the same location), storing B repeatedly alongside A invites contradiction, so A and B belong together in their own relation. Third normal form, informally: every non-key fact depends on the key, the whole key, and nothing but the key. Splitting relations this way is lossless (you can always reconstruct the original by joining), and the cost is paid at read time, which is exactly the trade dashboards reverse when they pre-join tables for speed.

New words in this session

  • database — software that stores tables safely on a server and answers queries from many users at once.
  • SQL — Structured Query Language; the standard language for asking tables questions ("select this from there where that").
  • query — one SQL sentence describing the answer you want.
  • primary key — the column that uniquely identifies each row of a table, like employee_id.
  • foreign key — a column holding another table's primary key, stitching tables together.
  • ER diagram — a picture of a database's tables and the keys linking them.
  • normalization — designing tables so every fact is stored in exactly one place, avoiding contradictions.
  • denormalization — deliberately repeating facts (pre-joining tables) to make reads faster, common in analytics.
  • flavour (dialect) — a version of SQL such as SQLite, PostgreSQL, MySQL, SQL Server or Oracle; same core language, small differences.

Full definitions are in the glossary.

Where industry keeps its data

The CSV you never get

  • In class: pd.read_csv("nifty.csv") — the data arrives as a file
  • In industry nobody emails you a CSV
  • orders, payments and policies live on servers, written by thousands of programs at once
  • UPI settles ~15 crore transactions a day; IRCTC opens lakhs of bookings in minutes
  • That needs software whose whole job is safe shared data: a database

What a database actually is

  • A server program that owns the company's tables
  • Many people and programs read and write at the same moment, safely
  • Rules enforced at write time: salary cannot be negative, every order has a customer
  • Analysts never touch files; they send sentences over the network

You already know the shape: a pandas DataFrame is a table too.

What SQL is, and why it is required

One sentence instead of a program

  • SELECT first_name, salary
  • FROM employees
  • WHERE salary > 80000;
  • You say WHAT you want, not HOW to walk the rows
  • pandas: df[df.salary > 80000][["first_name", "salary"]] — same idea
  • The database plans the fastest route; your sentence stays the same from 10 rows to 10 billion

The verbs you need today (and most days)

  • SELECT — which columns
  • FROM — which table
  • WHERE — which rows
  • DISTINCT — drop repeats
  • AS — rename a column in the answer

That is genuinely most of analytical SQL; joins come next session's worth of practice.

Why every data job lists SQL

  • The shared language: Python, Excel, Power BI and any web app can all speak it
  • Fifty years old and still at the top of developer-survey language rankings
  • Guards the data while hundreds of people use it at once
  • Interview round one for analyst, data engineering and data science roles

How industry stores its data

Our running example: an HR database

employees points at departments and jobs; manager_id points back into employees itself.

Keys: how tables point at each other

  • Primary key — the unique ID of a row: employees.employee_id
  • Foreign key — a column holding another table's ID: employees.department_id
  • The database rejects a department_id that does not exist — integrity by construction
  • ER diagram: the map of tables and keys (open it on the practice site)

Where data really lives

  • Operational database — today's transactions: orders placed now, balances as of now
  • Warehouse — years of history arranged for analysis; what analysts usually query
  • Files and lakes — logs, images, everything that is not naturally a table
  • Your Module-2 models ate from copies of these; SQL is how copies are taken

Normalization: why tables are split

One big sheet, three ways it breaks

  • emp_name | dept_name | dept_location | job_title | salary ← repeated on every row
  • Update anomaly — HR moves floor; you edit 200 rows, forget 3, and the sheet lies
  • Delete anomaly — the last HR employee leaves and the department itself vanishes
  • Insert anomaly — cannot record a new department until someone is posted there

The fix: each fact lives in exactly one place

  • employees(employee_id, name, job_id, salary, department_id)
  • departments(department_id, department_name, location)
  • jobs(job_id, job_title, min_salary, max_salary)
  • Change a location once, in one row — no contradictions possible
  • Joins stitch the picture back together when you ask

Normal forms, in plain words

  • 1NF — cells hold single values, not lists inside a cell
  • 2NF — facts depend on the whole key
  • 3NF — and nothing but the key
  • "the key, the whole key, and nothing but the key"
  • Dashboards deliberately denormalize: pre-joined wide tables trade storage for speed

One language, five flavours

The big five, and who runs them

  • SQLite — phones, browsers, small apps; lives inside your device
  • PostgreSQL — startups and modern data platforms
  • MySQL — web giants and UPI-scale apps
  • SQL Server — Microsoft shops, many Indian banks and insurers
  • Oracle — large enterprises, government, core banking

Same sentence, small accents

  • row limit: LIMIT 3 | TOP 3 | FETCH FIRST 3 ROWS ONLY | ROWNUM <= 3
  • join text: 'a' || 'b' vs CONCAT('a', 'b') vs 'a' + 'b'
  • Case rules, date arithmetic and auto-numbering also differ a little
  • Learn standard SQL once; pick up a workplace's accent in about a day
