The problem

You have spent two weeks on a data project. It finally works. Then your laptop plays up, or you "tidy up" a file and delete the one block that mattered, or a teammate emails you their copy and now there are two versions and nobody knows which is right. A week of work, gone or tangled. Later that night your script crashes with a wall of red text right before a deadline, and you have no idea what it is trying to tell you.

Two fears sit behind almost every beginner's stress with code: losing the work, and the work breaking. Today is the session that removes both. It is not about a new result. It is about keeping what you build safe, sharing it cleanly, and staying calm when something breaks.

The one idea

Git gives your project save points, exactly like the save points in a video game. Each time you reach a good spot you make one, and it keeps a full copy of the whole project at that moment, with a short note on what changed. You can walk back to any save point whenever you like. Nothing you save is ever truly lost.

GitHub is the place those save points live online. Push your project there and it is backed up, safe from a dying laptop, and shareable with a single link. A tidy public project on GitHub is also the first thing a recruiter opens.

And when code breaks, the red error is not an insult. It is a clue. The trick is to read it from the bottom up: the very last line names what went wrong, and the lines above show where. Once you can read the clue, most bugs stop being scary.

What you'll build today

  1. Turn a plain folder into a Git project, make two save points, and walk back to look at the earlier one, all inside a throwaway folder that cleans itself up.
  2. Publish your Session 1–3 labs as your first public GitHub repository, with a proper README and a pinned requirements.txt, so the work is safe and shareable.
  3. Read the five Python errors you will meet most often, bottom-up, and learn the one fix for each.
  4. Find and fix a bug with a calm, repeatable method, then guard your code with assert so a wrong assumption cannot sneak through.

By the end you can

  • Publish a clean, public GitHub repo with a clear README and a pinned requirements.txt.

For the mathematically curious (optional)

Everything above is enough to do the lab. This box is a bonus and none of it is needed to finish.

The mathematical object hiding under Git is the directed acyclic graph, a DAG. Draw each save point (each commit) as a dot, with an arrow pointing back to the save point it grew from, its parent. The arrows have a direction (child points to parent), and because time only moves forward you can never follow arrows and loop back to where you started. That is exactly what "directed" and "acyclic" mean.

Everything Git does is bookkeeping on that graph. git log walks it, a branch is a second arrow coming out of a node so history splits in two, and a merge is the one place the two lines fan back together into a node with two parents. Spotting a familiar abstract object living inside an everyday tool is the "mathematician in industry" instinct this whole course is training. If graphs are new to you, the picture-first version is in Graphs and DAGs.

New words in this session

  • repository (repo) — the folder Git watches, together with its full history.
  • commit — one save point: a snapshot of the whole project, with a message.
  • branch — a parallel line of history for trying something without risk.
  • remote / GitHub — the shared copy of your repo online; GitHub is where it lives.
  • push / pull — send your save points up to GitHub / bring others' back down.
  • traceback — the block of text Python prints when code breaks; read it bottom-up.
  • assert — a line that checks a belief and stops loudly if it is false.
  • virtual environment — a sealed toolbox of libraries just for one project.

Full definitions are in the glossary.
