  • Graphs and dags

The problem

You have spent two weeks on a data project. It finally works. Then your laptop plays up, or you "tidy up" a file and delete the one block that mattered, or a teammate emails you their copy and now there are two versions and nobody knows which is right. A week of work, gone or tangled.

The fear behind almost every beginner's stress with code is losing the work. Today is the session that removes it. It is not about a new result. It is about keeping what you build safe, sharing it cleanly, and being able to walk back to any earlier moment when something goes wrong.

The one idea

Git gives your project save points, exactly like the save points in a video game. Each time you reach a good spot you make one, and it keeps a full copy of the whole project at that moment, with a short note on what changed. You can walk back to any save point whenever you like. Nothing you save is ever truly lost.

GitHub is the place those save points live online. Push your project there and it is backed up, safe from a dying laptop, and shareable with a single link. A tidy public project on GitHub is also the first thing a recruiter opens.

How to use this page

Git runs at your terminal, not in a notebook — so there is nothing to install and nothing to open in Colab. The reference lower down is the whole class, in the order we did it, with every command explained in one plain line and the output you should expect. Read it straight through the first time, then keep it open as a lookup and type the lines at your own terminal, on your own project.

What this session covers

  1. Turn a plain folder into a Git project, make a few save points, and walk back to look at an earlier one.
  2. Recover a single file from an earlier save point — the one-line cure for "I deleted the block that mattered."

For the mathematically curious (optional)

Everything above is enough to do the work. This box is a bonus and none of it is needed to finish.

The mathematical object hiding under Git is the directed acyclic graph, a DAG. Draw each save point (each commit) as a dot, with an arrow pointing back to the save point it grew from, its parent. The arrows have a direction (child points to parent), and because time only moves forward you can never follow arrows and loop back to where you started. That is exactly what "directed" and "acyclic" mean.

Everything Git does is bookkeeping on that graph. git log walks it, a branch is a second arrow coming out of a node so history splits in two, and a merge is the one place the two lines fan back together into a node with two parents. Spotting a familiar abstract object living inside an everyday tool is the "mathematician in industry" instinct this whole course is training. If graphs are new to you, the picture-first version is in Graphs and DAGs.

New words in this session

  • repository (repo) — the folder Git watches, together with its full history.
  • commit — one save point: a snapshot of the whole project, with a message.
  • branch — a parallel line of history for trying something without risk.
  • remote / GitHub — the shared copy of your repo online; GitHub is where it lives.
  • push / pull — send your save points up to GitHub / bring others' back down.
  • virtual environment — a sealed toolbox of libraries just for one project.

Git & GitHub — the complete reference

Everything we did in class, in the order we did it. Git lives at the terminal, so there is nothing to install in a notebook — you type these lines at your own terminal, on your own project. Read it straight through the first time; after that, treat it as a lookup. Two habits carry you through almost everything: run git status constantly so you always know where you are, and remember that once something is committed it is very hard to truly lose.

The whole thing in one loop

Ninety-five percent of your Git life is four commands, in this order:

git status                     # where am I? what changed?
git add .                      # put the changes on the tray (stage them)
git commit -m "what changed"   # make a save point
git push                       # send it up to GitHub

Everything below is either setting this up the first time, or a small variation for when you need to look back at the past or undo something.

0. One-time setup (once per machine)

You do this once and never again on the same computer.

git --version
# -> git version 2.43.0        (anything 2.28 or newer is fine)

git config --global user.name  "Your Name"
git config --global user.email "you@example.com"
# Git stamps every save point with this name and email. This is where it comes from.

git config --global init.defaultBranch main
# The first line of history gets called "main". Set once, forever.

If an editor ever opens and traps you (it will be vim), press Esc, then type :wq and hit Enter. To avoid that forever, set a friendlier editor:

git config --global core.editor "nano"

1. Start a repository

Make an empty folder for the project and move into it first. Do not run this inside an existing project you care about.

git init
# -> Initialized empty Git repository in /home/you/analysis/.git/

git status
# -> On branch main / No commits yet / nothing to commit

That hidden .git folder is the repository — the whole history lives in there. Delete it and the history is gone, but your actual files are untouched: Git sits beside your work, not inside it. Get in the habit of running git status after almost every step; it always tells you where you are.

Now create a file by hand — say analysis.py containing print("Hello Git") — and look again:

git status
# -> Untracked files: analysis.py

Untracked means Git can see the file but is not yet watching it.

2. The save-point rhythm: add → commit → log

This is the heart of Git. Everything else is a variation on it.

git add analysis.py
# (silent — Git says nothing when it works)

git status
# -> Changes to be committed:  new file: analysis.py

The file is now staged — on the tray, ready to be saved, but not saved yet. Staging lets you choose exactly what goes into the next save point.

git commit -m "Start the analysis"
# -> [main (root-commit) 3f2a1b0] Start the analysis
#    1 file changed, 1 insertion(+)

git log --oneline
# -> 3f2a1b0 (HEAD -> main) Start the analysis

That is a save point. The short code 3f2a1b0 is its name (its hash). Now edit the file — add x = 10 and print(x + 5) — and see exactly what changed before you save again:

git diff
# -> +x = 10
#    +print(x + 5)

Reading git diff before every commit is a good habit — it is your last look at the change in your own words.

git add analysis.py
git commit -m "Add a calculation"
git log --oneline
# -> 9c4d2e1 (HEAD -> main) Add a calculation
#    3f2a1b0 Start the analysis

Two save points, newest on top. Write commit messages that finish the sentence "This commit will…": Add a calculation, Fix the date parsing, Clean the survey data. That is the whole loop.

3. Walk back to an earlier save point

You can visit any earlier save point and see the project exactly as it was.

git switch --detach 3f2a1b0     # use YOUR first hash from the log
# -> HEAD is now at 3f2a1b0 Start the analysis

Open analysis.py now and the calculation is gone — the folder really has been restored to that moment. The past is not a description of your files; it is your files, brought back. When you are done looking:

git switch -                    # back to where you were ("-" means "last place")

Nothing was lost by looking around.

4. Recover a single file from an earlier save point

This is the horror story from the start of class — you deleted the one block that mattered — and its one-line cure. Here you stay in the present and pull just one file back from an earlier save point.

Suppose you wreck analysis.py, or delete it entirely:

git status
# -> modified: analysis.py        (or 'deleted: analysis.py')

git restore --source=HEAD~1 analysis.py
# (silent) the file is back exactly as it was one save point ago

HEAD~1 means "one save point before now". Use HEAD~2 for two back, or paste a hash from git log to reach any point in the history. Confirm nothing is left over:

git diff HEAD~1 -- analysis.py
# -> (no output — the file matches that save point)

5. Undo recipes — what is reversible, and the one that bites

git restore --staged analysis.py        # take it off the tray, keep your edits
git restore --source=HEAD~2 analysis.py  # pull a file back from two save points ago
git commit --amend                       # fix the last commit's message or add a file
git reset --soft HEAD~1                   # undo the last commit, keep the changes staged

git restore analysis.py                   # throw away un-saved edits to a file — this one bites

Only the last one destroys work, and only work you had not committed yet. Everything you have committed is reachable; the rest of these recipes are all reversible. When in doubt, commit first, experiment second.

6. .gitignore — what not to save

You commit your code, not your data, your caches, or your secrets. A file named .gitignore lists patterns Git should pretend it cannot see. Create it by hand with lines like:

.ipynb_checkpoints/
__pycache__/
.venv/
*.csv
.env

Then:

git status
# -> the junk is gone from the listing; only .gitignore shows

git add .gitignore
git commit -m "Ignore junk and data"

Keeping data and virtual environments out of the repo is what keeps it small, clean, and safe to make public.

7. Put it on GitHub — connect and push

On github.com: New repository, give it a name (say analysis), and click Create. Leave it completely empty — do not tick "Add a README", a .gitignore, or a licence. (If you do, the first push is rejected; the fix is in the troubleshooting list below.)

git remote add origin https://github.com/you/analysis.git
git remote -v                    # check the address before you push
git push -u origin main
# -> * [new branch]  main -> main
#    branch 'main' set up to track 'origin/main'.

Refresh the GitHub page and your files are there. Your work now exists on a second machine — if the laptop dies, the work survives. From now on, sending new save points up is just:

git push

8. Clone — copy an existing project

To get a full copy of a project that already lives on GitHub (mine, a teammate's, or your own on another computer):

git clone https://github.com/you/analysis.git

This is how you fetch other people's code, and how a recruiter fetches yours.

9. Branches — a safe place to try an idea (optional)

A branch is a parallel line of history. You can try a risky change on a branch and, if it does not work out, throw the branch away with the main line untouched.

git branch                      # list branches; * marks the one you are on
git switch -c feature           # create a branch AND switch onto it
# ... make a commit or two on the branch ...
git switch main                 # switch back to the main line, untouched
git merge feature               # bring the branch's work into main
git branch -d feature           # tidy up the merged branch

You can do everything in this course on main alone; reach for a branch once you want to try something without risking what already works.

When it goes wrong — the four that actually happen

Push asks for a password and rejects yours. GitHub turned off password logins in 2021. It wants a Personal Access Token instead: on github.com go to Settings → Developer settings → Personal access tokens → Tokens (classic) → Generate new, tick the repo box, and copy the token. Paste that token where Git asks for the password. (Generate one before you need it, not in a panic.)

"Updates were rejected because the remote contains work you do not have." You ticked "Add a README" when creating the repo, so GitHub already has a commit you don't. Bring it down, then push:

git pull --rebase origin main
git push -u origin main

"Please tell me who you are." You skipped section 0 on this machine. Run the two git config --global user.name / user.email lines.

An editor opened and you are stuck (this is vim). Press Esc, type :wq, and press Enter. Then set a friendlier editor for next time: git config --global core.editor "nano".

One-screen cheat sheet

# --- setup (once per machine) --------------------------------------------
git config --global user.name  "Your Name"
git config --global user.email "you@example.com"

# --- start a repo --------------------------------------------------------
git init                          # turn this folder into a repository
git status                        # where am I? what changed? (run constantly)

# --- the save-point rhythm -----------------------------------------------
git add <file>      /  git add .  # stage one file / everything
git diff                          # see what changed before you save
git commit -m "message"           # make a save point
git log --oneline                 # list the save points, newest on top

# --- look back / recover -------------------------------------------------
git switch --detach <hash>        # visit an earlier save point
git switch -                      # come back to where you were
git restore --source=HEAD~1 <f>   # bring one file back from a save point

# --- undo (all reversible except a bare restore of un-saved edits) -------
git restore --staged <file>       # unstage, keep edits
git commit --amend                # fix the last commit
git reset --soft HEAD~1           # undo last commit, keep changes staged

# --- GitHub --------------------------------------------------------------
git remote add origin <url>       # connect to an EMPTY GitHub repo
git push -u origin main           # first push; after this, just: git push
git clone <url>                   # copy an existing project

# --- the everyday loop (95% of Git) --------------------------------------
git status  &&  git add .  &&  git commit -m "..."  &&  git push

1 · Save points: never lose your work

The horror we are escaping

  • report.py, report_v2.py, report_final.py, report_final_v3.py …
  • report_final_v3_FINAL(2).py — and you no longer know which one works.
  • You emailed a file to a teammate; now two copies drift apart.
  • You deleted a working block 'to clean up' and cannot get it back.
  • You changed three things to fix a bug and now nothing runs.

What save points give you instead

  • One folder, one history. No more _final copies.
  • A time machine: walk back to any earlier save point, safely.
  • A labelled log of what changed, when, and why.
  • A way for several people to work on the same code without chaos.
  • A shareable, reproducible record of how a result was produced.

Git is a time machine for your project. Once something is saved, you can always get it back.

2 · Where your work lives

Four places your work can be

add stages it; commit saves a save point; push shares it; pull brings others' work back.

The staging area, in plain words

  • You rarely want to save EVERYTHING you touched in one go.
  • Staging lets you pick exactly which changes belong in this save point.
  • Think of it as a tray: you place items on it, then commit the tray.
  • This is why a save point can be neat and focused, not a big dump.

The five commands you'll use 95% of the time

The add → commit → log rhythm, for real

  • Each add-then-commit writes one save point; git log --oneline lists them newest-first, each with a short id and its message.

CODE # a fresh folder, already run: git init -b main git add analysis_notes.txt # put the file on the tray git commit -m "Start the analysis notes" # ...edit the file, then repeat the same two steps... git add analysis_notes.txt git commit -m "Add the day-2 finding" git log --oneline # the save-point history OUTPUT ▸ 2889bf9 Add the day-2 finding d84b7d5 Start the analysis notes

Git day to day — the commands you'll actually type

  • Every few minutes
  • Sync · look back
  • git status
  • what changed, and what's staged
  • git add <file>
  • stage it · git add -p to pick pieces
  • git commit -m "message"
  • write one save point

  • git pull / git push
  • get teammates' work / publish yours

3 · GitHub — safe online, shareable, and your portfolio

Git vs GitHub — not the same thing

  • Git is the tool on your computer that keeps the save points (works offline).
  • GitHub is a website that hosts a copy of your project online.
  • GitHub is the 'remote' in our diagram — the shared, backed-up copy.
  • Push your project there and a dying laptop can no longer lose it.
  • Other hosts exist (GitLab, Bitbucket); GitHub is the most common.

How a repo is shared

Everyone pushes to and pulls from the same GitHub remote; the public can read it.

Put your project on GitHub — connect and push

  • Do this once per project: make an empty repo online, point your folder at it with remote add, then push. To get someone else's project instead: git clone <url>.

CODE # 1. on github.com: New repository -> name it -> Create # (leave it EMPTY: no README, no .gitignore) # 2. in your project folder (files already created, commits made): git remote add origin https://github.com/you/carbon-analysis.git git branch -M main # make sure the branch is called main git push -u origin main # first push; after this just: git push OUTPUT ▸ # your code is now on GitHub — refresh the page to see it # from now on: git add . -> git commit -m "..." -> git push

The README: the front page of your project

  • README.md is the first thing anyone sees when they open your repo.
  • It says what the project does, how to run it, and what it found.
  • Written in Markdown — plain text with simple, readable formatting.
  • A repo with no README looks abandoned; a good one looks professional.

A clean public repo with a clear README is a portfolio piece. It is often the first thing a recruiter actually opens.

4 · Reproducibility — runs the same for everyone

The other half of professionalism

  • 'It works on my machine' is the classic excuse — and it is not good enough.
  • A result you cannot reproduce is a result nobody can trust.
  • Reproducibility = anyone can re-run your work and get the same answer.
  • Two simple habits get you most of the way there.

A virtual environment is an isolated toolbox

  • No clashing versions between projects.
  • Delete it freely; your project is safe.
  • python -m venv .venv creates one.
  • Activate it before you work.

Each project gets its own sealed set of packages, at their own versions.

requirements.txt: pin your versions

  • A small text file listing every package and its exact version.
  • e.g. pandas==2.2.0, numpy==1.26.4, scikit-learn==1.4.2
  • pip freeze > requirements.txt writes it for you.
  • Anyone can recreate your exact toolbox with one install command.
  • Commit it to the repo — it is part of the project.

Notebook hygiene — for reproducible results

  • Avoid
  • Cells run out of order, top-to-bottom broken
  • Hidden state from deleted cells
  • Huge committed outputs and plots in the .ipynb
  • Hard-coded paths like C:/Users/me/Desktop
  • Do instead
  • Restart kernel & run all, top to bottom
  • If it only works out of order, it is broken
  • Clear outputs before committing
  • Use relative paths from the repo root

5 · When code breaks — stay calm

Everyone's code breaks — that is normal

  • Errors are not failures; they are the computer telling you what is wrong.
  • A Python error message is a clue, not an insult.
  • The skill is reading the clue calmly, not panicking or guessing.
  • We will learn to read tracebacks and a simple, repeatable method.

Reading a Python traceback — bottom-up

The last line is the real error. Read upward to find where it came from.

A real traceback, read bottom-up

  • The last line is the real error — a KeyError for 'close_price'; read upward and line 2, the misspelled key, is where it broke.

CODE def load_price(one_day): return one_day["close_price"] # typo: data has "clse_price" def run_report(): one_day = {"clse_price": 100} return load_price(one_day) run_report() OUTPUT ▸ Traceback (most recent call last): File "report.py", line 8, in <module> File "report.py", line 6, in run_report File "report.py", line 2, in load_price KeyError: 'close_price'

Five errors you will meet constantly

Two ways to look inside a running program

  • Quick & dirty
  • Proper & powerful
  • print debugging
  • Drop print() at suspicious spots
  • See the value of a variable at that moment
  • Crude but instant — everyone does it
  • Remember to remove them afterwards
  • the debugger
  • breakpoint() pauses execution there
  • Inspect every variable, step line by line
  • pdb is built into Python — nothing to install
  • More powerful once you are comfortable

Print-debugging: watch the average go wrong

  • The prints expose the bug: there are 3 items, but the code divided by 2 and got 6.0 where the true average is 4.0.

CODE def average_with_prints(numbers): total = 0 for one_number in numbers: total = total + one_number print(" added", one_number, "-> running total is now", total) print(" number of items is", len(numbers)) answer = total / 2 # the suspicious line print(" we divided by 2 and got", answer) return answer average_with_prints([2, 4, 6]) OUTPUT ▸ added 2 -> running total is now 2 added 4 -> running total is now 6 added 6 -> running total is now 12 number of items is 3 we divided by 2 and got 6.0

Guard your assumptions with assert

  • An assert is one line that checks a belief and stops loudly if it is false.
  • e.g. assert len(prices) > 0, 'no prices loaded' — catches an empty table before it causes a weird error later.
  • It turns a silent wrong assumption into a clear, early complaint.
  • Sprinkle a few where your code assumes something must be true.

Guard an empty list with assert

  • The good call returns 6.0; the empty list trips the assert and stops with a clear message, instead of a confusing error further down.

CODE def safe_average(numbers): assert len(numbers) > 0, "cannot take the average of an empty list" return sum(numbers) / len(numbers) print("safe_average([4, 8]) =", safe_average([4, 8])) try: safe_average([]) except AssertionError as the_error: print("Guard worked. Message:", the_error) OUTPUT ▸ safe_average([4, 8]) = 6.0 Guard worked. Message: cannot take the average of an empty list

A calm method beats frantic guessing

Reproduce, read, isolate, fix one thing, verify. Then repeat if needed.

Change one thing at a time, then check. Debugging is the scientific method applied to your code.

Change one line, then check

  • Same input, one changed line — divide by len(numbers), not 2 — turns 6.0 into the correct 4.0, and the check confirms the fix.

CODE def average(numbers): # BUG: divides by 2, not the count return sum(numbers) / 2 print("buggy :", average([2, 4, 6])) def average_fixed(numbers): # only one line changed return sum(numbers) / len(numbers) print("fixed :", average_fixed([2, 4, 6])) print("check :", average_fixed([2, 4, 6]) == 4.0) OUTPUT ▸ buggy : 6.0 fixed : 4.0 check : True

Common first-timer traps

  • Avoid

  • No README — the repo looks abandoned
