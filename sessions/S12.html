The problem

A bank wants to flag customers who might close their account, so it exports its customer table and hands it to your team. You open the file and your heart sinks. Ages are missing — hidden as the sentinel 999. Income has blanks in the middle of the numbers, and a couple of customers earn ten times everyone else. One column says "Mumbai" while another row says " mumbai " with stray spaces and lower-case letters. Rows are duplicated, every row says "West" for region, and there is a column that secretly contains the answer.

No model can learn from this. Before anyone trains anything, someone has to get the data into a shape a model can actually use. That someone is you, and this is where working data scientists spend most of their time. Today is about that job, and it is one of the most useful days in the whole course, whatever your background.

The one idea

The same facts, written a different way, can turn an impossible problem into an easy one.

Picture two groups of dots on a chart, arranged as two rings, one small ring sitting inside a bigger ring. You want a rule that tells the two groups apart. A straight line cannot do it: whichever way you draw the line, it slices through both rings. The problem looks hard.

Now measure one new thing about each dot: its distance from the centre. The inner ring is close to the centre, the outer ring is far. So a single cut on that one number, "closer than this, or further" splits the two groups perfectly. Nothing about the dots changed. We just described each dot with a better number, and the hard problem dissolved.

That is feature engineering. A "feature" is just a column you feed the model. When you choose good columns, even the simplest model wins. When you feed it raw mess, the fanciest model still fails. Choosing how to write the data down is choosing how hard the model's job will be.

What you'll build today

One deliberately ugly customer table and one model family. We leave the model alone and change only the features, step by step, and watch the score climb:

  1. Build the messy dataset in code and save it to data/messy_customers.csv — missing values, disguised 999s, untidy city text, outliers, a correlated twin, a leakage column, a constant column, a unique ID and duplicate rows.
  2. Look before touching anything: profile the table, count the blanks, spot the sentinels and the duplicates.
  3. Fit a plain baseline model on the raw mess and record its accuracy — our "before" number.
  4. Run the messy-data playbook: unmask 999, tidy the text, fill missing values, drop dead weight, cap outliers and log the skewed income.
  5. Engineer features: split the date into month and weekday, build an interaction and a polynomial column, then remove the correlated twin and the leakage column.
  6. One-hot the city, scale the numeric columns (fitting on the training split only), and fit the same model again — and see the "after" number.
  7. Hold the model fixed and improve only its features, then watch the score climb.

For the mathematically curious (optional)

Everything above is enough to do the lab. This box is the extra depth, and none of it is needed to finish.

Today's mathematical object is representation. A model can only fit the functions its shape allows. A linear model fits straight lines and flat planes and nothing else, so its reachable functions are exactly the linear ones in whatever coordinates you hand it. When you engineer a feature, you are applying a map φ that sends each input x to a richer description φ(x), and then fitting a linear rule in that new space. The concentric rings are the clean example: in the raw coordinates (x, y) the two classes are not linearly separable, but under the map φ(x, y) = (x, y, √(x²+y²)) a single hyperplane separates them exactly. The data never moved; the coordinate system did. This is the same idea a kernel makes implicit, and the same idea a neural network learns for itself in the next session. One-hot encoding is the special case of φ that sends a category to an indicator vector, and standardisation is the affine map x ↦ (x − μ)/σ that makes each coordinate comparable so a distance is fair. Choosing a representation is choosing which functions are reachable, and it is usually cheaper and more reliable than reaching for a fancier model.

New words in this session

  • feature — an input column you feed a model. Its size and city are features of a customer.
  • feature engineering — building better input columns so a simple model can succeed.
  • representation — the particular way you write the data down; changing it changes what the model can learn.
  • one-hot encoding — turning a text category into one 0/1 column per value, so no fake order is implied.
  • standardisation (scaling) — shifting and stretching a column so it is centred at 0 with spread about 1, putting all columns on a common footing.
  • missing value (NaN) — a blank cell; the honest way to record "we do not know".
  • sentinel value — a fake stand-in for missing, like 999 or "NA", that must be unmasked to a real NaN.
  • interaction feature — a new column built from two others together (weekend AND rain), carrying signal neither column holds alone.

Scaling

  • Put every column on one footing

Before and after scaling

  • Who needs it: distance models — k-means, kNN, SVM.
  • Who needs it too: gradient models — logistic regression, neural nets.
  • Who ignores it: trees (random forest, boosting) split one column at a time.

Before: income dwarfs age. After scaling: both count equally.

Standardisation (z-score)

  • Subtract the average, divide by the spread — centred at 0, spread ≈ 1.
  • μ — the mean; σ — the spread (standard deviation)
  • z — how many spreads above or below the average
  • Fit μ and σ on the TRAIN rows only (leakage).

Min-max scaling

  • Subtract the min, divide by the range — every value squashed into 0 to 1.
  • x_min, x_max — smallest and largest in the column
  • One extreme value stretches the range — a known weakness
  • Take x_min and x_max from the TRAIN rows only (leakage).

Taming skewed money with a log

  • Who needs it: regressions on money — income, spend, amount.
  • Helps linear and neural-net models most.
  • Trees read rank only, so they barely feel the skew.

Incomes and amounts have long right tails; a log pulls them into shape.

Encoding categories

  • Turn words into numbers

Models do sums; your data has words

  • A model can only add and multiply numbers.
  • But columns hold 'Pune', 'Gold', 'Yes', dates, text.
  • Turn each into numbers — without inventing a fake order.
  • Numbering cities 1, 2, 3 tells the model a lie.

One-hot encoding

  • Who needs it: every scikit-learn model — numbers only.
  • Helps most: linear, logistic, kNN, neural nets.
  • Watch out: 500 cities → 500 columns — prefer target encoding.

Each distinct value becomes its own 0/1 column. No fake order.

One-hot, written as maths

  • A category becomes 0/1 switches — one column per value, exactly one is 1.
  • c — the category in this row; v1 … vm — its possible values
  • 1[c = vj] — 1 when c equals vj, else 0
  • No order implied — Delhi, Mumbai, Pune are separate switches

Dates become numbers

One date unfolds into many columns

  • Who reads it: any model — these are plain numbers.
  • Helps most: time-aware models — forecasting, sales.
  • Local knowledge (Diwali, salary week) is gold here.

Day-of-week, month, is_weekend, is_holiday, days-to-festival, lagged sales.

Free text is a niche — and a deeper topic

  • Dates and categories cover most business columns.
  • Free text (reviews, complaints) needs its own text pipeline first.

Build richer columns

  • Interactions, polynomials, and domain knowledge

Interaction features: one column × another

Polynomial features: make the data richer

  • Give the model x, x², x³ — a straight line becomes a curve.
  • Instead of making the model more complex, we make the data richer.
  • Who needs it: linear and logistic regression on curved truths.
  • Who ignores it: trees — splits already find curves on their own.

Left: with only x, the best line can't bend. Right: add an x² column and the SAME model fits the curve.

Domain knowledge: columns the data never told you

Feature selection

  • You built 100 columns — now keep the good ones

Drop the columns that add nothing

Keep one of each pair of twins

  • Two columns that move together carry the same information twice.
  • correlation(A, B) close to +1 or −1 → keep one, drop the other.
  • Redundant columns slow the model — and distance models double-count them.
  • Classic example: 'years of experience' and 'age' in the same dataset.
  • Rule of thumb: drop one of any pair with |corr| above ~0.9 — with domain judgement.

Let the model rank your columns

  • Let the model do the sorting, then fit your real model on the shortlist only.

Leakage

  • Fit on the training split only

Never leak the answer into your columns

  • Fit every scaler and encoder on the TRAIN rows only.
  • Fitting on all the data lets the test set leak in.
  • Then your score looks great — and fails in production.
  • A scikit-learn Pipeline enforces train-only for you.

Key takeaways

  • A 'feature' is just a column you feed the model — choosing good ones is the real work.
  • The same facts, written better, turn a hard problem easy (rings → distance).
  • Turn words, dates and text into numbers: one-hot, scaling, calendar columns.
  • Build richer columns — interactions, polynomials, domain features — then SELECT: drop constant and twin columns, keep the ranked best.
  • Clean by a fixed playbook: look → types → dates → dupes → missing → categories → check.
  • Fit scalers and encoders on the TRAIN split only — never leak the answer.
