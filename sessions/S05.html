The problem

You have a table. It might be a year of sales, a month of delivery times, or a spreadsheet a colleague emailed you with no explanation. Somewhere in those rows is something worth knowing — which product is slipping, which month broke the trend, which two numbers move together. You cannot find it by scrolling, and even once you have found it, a column of numbers will not convince anybody.

So you draw it. But a chart drawn badly is worse than no chart: it buries the pattern, or it makes a small difference look like a crisis. The skill is not learning chart syntax. It is choosing the picture that answers the question you actually asked, and drawing it honestly.

The one idea

Every seaborn chart is the same function call.

You hand it a table, say which column runs across, which runs up, and which one decides the colour. Change the verb and you get a different chart.

sns.scatterplot(data=tips, x="total_bill", y="tip", hue="sex")
sns.barplot(data=tips,     x="day",        y="tip", hue="sex")
sns.boxplot(data=tips,     x="day",        y="tip", hue="sex")

Three different charts, one sentence. That is why seaborn is worth an evening: you learn data, x, y and hue once, and ten chart types come free. The rest of today is knowing which verb answers which question.

For the mathematically curious (optional)

Everything above is enough to do the lab. This box is extra depth, and none of it is needed to finish.

A table with n numeric columns is a set of points in n-dimensional space: one point per row, one axis per column. The iris table is 150 points in four dimensions. You cannot see four dimensions, and a page has only two, so every chart you draw is a projection — a map from that high-dimensional space down to the two directions the eye can read.

Choosing a chart is choosing that projection. A scatter of petal length against petal width keeps two coordinates and discards the other two. A hue smuggles a third back in as colour. A pairplot is the honest admission that you do not yet know which projection matters, so it draws every two-dimensional one at once and lets you pick.

That is a real choice with real consequences. Project badly and three clearly separate groups collapse into one blob; project well and the structure is obvious at a glance — which is exactly what happens when you compare the sepal panels of the iris pair plot with the petal ones. Today you choose the projection by hand, by picking columns. In Session 11 (principal component analysis) we compute the projection that preserves as much of the spread as possible, so the machine picks it for you. The pairplot you draw today is the picture that PCA later automates.

New words in this session

  • distribution — the shape of a single column of numbers: where they cluster and how spread out they are.
  • histogram — a chart that chops one column into bins and counts each.
  • median — the middle value; half the data sits above it, half below.
  • outlier — a value far from the rest, worth asking about rather than deleting.
  • correlation — a number from −1 to +1 for how strongly two columns move together in a straight line.
  • skew — a distribution with a long tail on one side.
  • facet — repeating the same chart once per category, side by side.
  • axes object — matplotlib's name for a single panel of a figure; the thing you pass as ax= to draw into a chosen panel.

4 · Which chart answers which question

  • The judgement half — this is where the marks are

Start from the question, never from the chart

  • The beginner move is 'I want a pie chart'. The professional move is 'what am I trying to show?'
  • Comparing categories → bar
  • A trend through time → line
  • The shape of one column → histogram or box
  • The relationship between two → scatter
  • Parts of a whole → stacked bar (a pie only for two or three slices)
  • Get the question right and the chart almost chooses itself.

Question → chart, with an Indian-industry example

Two charts, same data, different question

  • countplot(x='day')
  • How MANY bills arrived each day
  • Height = a count of rows
  • Answers: when is the restaurant busy?
  • No y argument
  • barplot(x='day', y='tip')
  • The AVERAGE tip on each day
  • Height = a mean of y
  • Answers: when do people tip well?
  • y is required

1 · Meet your data: a table

  • Part A — asking the table questions

Why it is worth learning SQL

  • Most company data does not live in a spreadsheet. It lives in a database: many tables that link to each other.
  • Orders, customers, payments, inventory — separate tables, connected.
  • SQL is the one language used to ask questions of that data, everywhere: banks, Flipkart, Razorpay, hospitals, government.
  • If you can write SQL, you can get the data yourself, instead of waiting for someone to export a file for you.

A table: rows and columns, nothing more

One row is one record (an order); one column is one field (city, amount). That is the whole picture.

Build the orders table in code

  • A dictionary of lists becomes the table: each key is a column, each list its values.

2 · The five words that do most of the work

Five words cover most real questions

  • SELECT — which columns you want.
  • FROM — which table you are reading.
  • WHERE — keep only the rows that pass a test.
  • GROUP BY — bundle rows together to summarise them.
  • ORDER BY — arrange the output.
  • Master these five and you can answer a huge share of business questions.

Two core moves: keep some rows, keep some columns

WHERE keeps rows (the ones that pass a test); SELECT keeps columns (the ones you ask for).

Keep just the Pune orders (WHERE + SELECT)

  • WHERE keeps only the rows that pass the test; SELECT keeps only the three named columns.

CODE OUTPUT ▸ import duckdb # run SQL straight on the DataFrame query = """ SELECT city, product, amount FROM orders WHERE city = 'Pune' """ duckdb.sql(query).df() city product amount 0 Pune Pen 120 1 Pune Notebook 380 2 Pune Marker 200

How to read a query (the order it actually runs)

  • You WRITE it as: SELECT … FROM … WHERE … GROUP BY … ORDER BY.
  • The database RUNS it roughly as: FROM → WHERE → GROUP BY → SELECT → ORDER BY.
  • So it filters rows first, then groups them, then picks the columns, then sorts.
  • Knowing this order explains most 'why doesn't my query work?' moments.

The one query shape you'll reuse forever

  • Almost every question you ask fits this skeleton — fill in the clauses you need, drop the ones you don't.

SQL SELECT city, SUM(amount) AS total -- columns + summaries FROM orders -- the table WHERE amount > 0 -- keep some rows (before grouping) GROUP BY city -- one row per group HAVING SUM(amount) > 1000 -- keep some groups (after grouping) ORDER BY total DESC -- sort the result LIMIT 10; -- just the top few HOW IT RUNS ▸ # runs in this order: # FROM -> WHERE -> GROUP BY -> HAVING -> SELECT -> ORDER BY -> LIMIT

3 · Joins — putting two tables together

Why the data is split across tables

  • We don't repeat a customer's full name on every one of their orders.
  • Instead: a customers table and an orders table, linked by a shared column (a key, like cust_id).
  • Store each fact once, in one place. Fix a phone number once, not on every order.
  • A join puts the two tables back together when you need them combined — exactly the pandas merge from S3, in database words.

A join stitches two tables on a shared column

Match rows where cust_id agrees, then carry both tables' columns into the result.

Stitch each order to its customer (INNER JOIN)

  • ON matches rows where customer_id agrees, then carries columns from both tables into one.

CODE query = """ SELECT orders.order_id, customers.name, customers.city, orders.amount FROM orders INNER JOIN customers ON orders.customer_id = customers.customer_id """ duckdb.sql(query).df() OUTPUT ▸ order_id name city amount 0 102 Asha Pune 120 1 103 Ravi Mumbai 980 2 104 Neha Pune 640 3 101 Asha Pune 450

The four kinds of join

  • Inner: only the matches.
  • Left: keep all left rows.
  • Right: keep all right rows.
  • Full outer: keep everything.

They differ only in which unmatched rows you keep.

Inner vs left join — a costly difference

  • INNER JOIN
  • Customers WITH at least one order
  • Customers who never ordered disappear
  • Your count can silently shrink
  • Use when you only want matched records
  • LEFT JOIN
  • ALL customers, orders attached if any
  • Never-ordered customers kept (blank orders)
  • Count of customers preserved
  • Use when the left table is your 'spine'

4 · Summarising: group rows, add a running total

GROUP BY: split, summarise, combine

Split the rows into groups, apply a summary to each, combine into one row per group.

Total sales per city with GROUP BY

  • Eight order rows collapse to one summary row per city; SUM adds the amounts in each group.

CODE OUTPUT ▸ query = """ SELECT city, SUM(amount) AS total_amount FROM orders GROUP BY city ORDER BY total_amount DESC """ duckdb.sql(query).df() city total_amount 0 Mumbai 720.0 1 Pune 700.0 2 Delhi 560.0

The grouping rule that trips everyone up

  • With GROUP BY, every column you SELECT must either be in the GROUP BY or wrapped in a summary.
  • Why: each output row stands for a whole group, so a plain column has many values and no single answer.
  • SUM, COUNT, AVG, MIN and MAX collapse those many values into one.
  • Forgetting this is the number-one GROUP BY error — the database will complain.

WHERE vs HAVING — filter before, or after, grouping

  • WHERE
  • Filters individual rows
  • Runs BEFORE grouping
  • Cannot use a total like SUM
  • e.g. WHERE city = 'Pune'
  • HAVING
  • Filters whole groups
  • Runs AFTER grouping
  • CAN use totals like SUM
  • e.g. HAVING SUM(amount) > 10000

Two shapes of summary: collapse the rows, or keep them

GROUP BY collapses each group to one row; a window keeps every row and adds a column.

A window in action: a running total

  • Running totals.
  • Rank within a group.
  • Change from the previous row.
  • Moving averages.

Every day's bar is still there; the line is the cumulative total 'so far'.

Add a running total with a window function

  • SUM ... OVER keeps every month and adds a column: revenue accumulated so far.

CODE query = """ SELECT month, revenue, SUM(revenue) OVER (ORDER BY month_number) AS revenue_so_far FROM monthly ORDER BY month_number """ duckdb.sql(query).df() OUTPUT ▸ month revenue revenue_so_far 0 Jan 120 120.0 1 Feb 150 270.0 2 Mar 90 360.0 3 Apr 200 560.0 4 May 170 730.0

Common first-timer traps — SQL and charts

  • Avoid
  • SELECT * everywhere (slow, unclear)
  • Forgetting to group every selected column
  • An inner join that silently drops rows
  • Truncated / non-zero bar axes
  • Rainbow colours for ordered data
  • Do instead
  • Select only the columns you need
  • Group or summarise every selected column
  • Left join when you need the full spine
  • Start bar axes at zero
  • One clean colour scale

Key takeaways

  • Your data is a table; SQL is a small, English-like language for asking it precise questions.
  • SELECT keeps columns, WHERE keeps rows; GROUP BY summarises, JOIN combines two tables.
  • Inner vs left join, and WHERE vs HAVING, decide which rows survive.
  • DuckDB runs SQL straight on a DataFrame, CSV or Parquet with zero setup.
  • A page has only two directions: pick the chart from the question, and keep it honest.
  • Start bar axes at zero, use one or two colours, and make each chart say one thing.
