What a model is

A "mathematical model" sounds heavy. It is not. This page explains the idea in plain words, with a small example, in about ten minutes. No proofs. Read it before the modelling session and the rest will feel obvious.

The problem it solves

Real problems are messy. "Will this junction jam at rush hour?" "What should we charge to deliver this parcel?" "How much crop will this season give us?" You cannot hand a question like that to a computer. It is too vague, and there is far too much detail.

A model is how you shrink a messy real problem down to a small, tidy version that a computer, or a careful person, can actually work on. You throw away almost everything and keep only the handful of things that matter for the one question you are asking.

Think of a map. A map of Pune is not Pune. It leaves out every tree, every pothole, every person. That is exactly why it is useful: it keeps only the roads, because roads are what you need to get from one place to another. A model is a map of a problem. It is never the whole truth, and it is not trying to be. We do not ask "is this model true?" We ask "is it useful for the decision in front of me?"

There is a famous line for this, worth remembering: all models are wrong, but some are useful.

The five parts every model has

Here is the pleasant surprise. However different two problems look, the model you build for each has the same five parts. Once you can name these five for any problem, you can model.

  • Variables. The things you want to find, or the things you get to choose. Give each a clear name and a unit. "L = number of cars waiting", not just "L".
  • Parameters. The numbers the world hands you: rates, costs, capacities. Fixed for one run of the model, but you can change them to ask "what if?". "Cars arrive at 30 per minute" is a parameter.
  • Constraints. The rules the answer must obey. A queue length cannot be negative. You only have so many trucks. Money in must equal money out.
  • Objective. The one quantity you are trying to make as good as possible. Smallest cost, shortest wait, biggest yield. Some models have no objective at all (you are just adding things up), and that is fine too.
  • Assumptions. Every simplification you made, written down. "Cars arrive at a steady average rate." "Rainfall is the main thing that drives yield." The danger in a model is never the assumption you wrote down. It is the one you made without noticing.

A quick test that trips up beginners: is something a variable or a parameter? Ask "can the model choose it?" If yes, it is a variable. If the world just hands it to you, it is a parameter.

A tiny worked example

Question: how long is the queue at a single traffic signal?

  • Variable: L, the number of cars waiting.
  • Parameters: how fast cars arrive (say 3 per minute), how fast the green light clears them (say 4 per minute).
  • Constraint: L can never be below zero.
  • Objective: here we only want to predict L, so there is nothing to optimise.
  • Assumptions: one queue, one signal, arrivals are steady on average, no breakdowns.

That is a complete model, written in plain words, before a single line of code. The code comes after, and it is short.

It goes in a loop

You do not get a model right on the first try, and you are not supposed to. The honest picture is a loop: watch the real problem, simplify it, write it down, solve or simulate it, then check the answer against reality. If it is off, you change an assumption and go round again. This loop is called the modelling cycle. The step beginners skip is the last one, checking against reality. A number nobody has checked is just an opinion in a nice font.

Why industry cares

A model lets you answer a question before you spend the money or the time. A retailer can test a stocking plan on a laptop instead of losing crores finding out the hard way. A logistics firm can price a parcel instead of guessing. And because the assumptions are written down, a team can argue about a stated number in a meeting rather than about vague feelings. That is what an employer is really paying a mathematician for: not a formula, but the judgement to turn a fuzzy problem into something solvable.
